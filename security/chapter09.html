09 Bảo mật API & Secrets Management

API là "cửa ngõ" phổ biến nhất bị tấn công trong kiến trúc hiện đại — và quản lý bí mật (secrets) sai cách là nguyên nhân rò rỉ dữ liệu hàng đầu.

Input Validation nghiêm ngặt

validation_voi_dto.ts 
// Nhắc lại DTO đã học ở Full-Stack JS chương 22 (NestJS)
import { IsEmail, IsString, MinLength, MaxLength } from 'class-validator';

export class DangKyDto {
    @IsEmail()                          // PHẢI đúng định dạng email
    email: string;

    @IsString()
    @MinLength(8)                          // mật khẩu tối thiểu 8 ký tự
    @MaxLength(100)                          // giới hạn tối đa - chống tấn công "quá tải" bằng chuỗi cực dài
    matKhau: string;
}

Quản lý Secrets đúng cách

SAIĐÚNG
Hardcode API key trực tiếp trong codeĐọc từ biến môi trường (process.env.API_KEY)
Commit file .env lên GitThêm .env vào .gitignore (đã học ch.2)
Dùng chung 1 secret cho mọi môi trườngSecret RIÊNG cho development/staging/production
Log ra secret khi debugChe/ẩn (mask) thông tin nhạy cảm trong log
rate_limiting_api.js 
// npm install express-rate-limit
const rateLimit = require('express-rate-limit');

const gioiHan = rateLimit({
    windowMs: 15 * 60 * 1000,        // cửa sổ 15 phút
    max: 100,                              // tối đa 100 request/IP trong cửa sổ đó
    message: 'Quá nhiều request, vui lòng thử lại sau.',
});

app.use('/api/', gioiHan);       // áp dụng cho toàn bộ route /api/*
// Nhắc lại khái niệm Rate Limiting đã học sâu hơn ở System Design chương 9
Quan trọng
Với hệ thống dùng tổ chức đám mây (AWS, GCP, Azure...), nên dùng dịch vụ Secrets Manager chuyên dụng thay vì chỉ file .env — cho phép xoay vòng (rotate) secret định kỳ tự động và kiểm soát quyền truy cập chi tiết hơn nhiều.

Bảo mật API cần validation nghiêm ngặt đầu vào (DTO), rate limiting chống lạm dụng, và quản lý secrets đúng cách (biến môi trường, không commit Git, tách biệt theo môi trường).
