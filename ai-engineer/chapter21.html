Chương 21 — Tối ưu Chi phí & Hiệu năng LLM

Gọi API LLM tính phí theo token — ở quy mô production, chi phí có thể tăng vọt nếu không tối ưu cẩn thận.

Prompt Caching — giảm chi phí cho phần prompt lặp lại

prompt_caching.py 
# System prompt dài, LẶP LẠI ở mọi request -> đánh dấu để cache
response = client.messages.create(
    model="YOUR_CURRENT_CLAUDE_MODEL_ID",
    max_tokens=500,
    system=[{
        "type": "text",
        "text": VAN_BAN_HUONG_DAN_RAT_DAI,     # VD: tài liệu sản phẩm dài hàng nghìn từ
        "cache_control": {"type": "ephemeral"}    # cú pháp/chính sách cache tùy API và model
    }],
    messages=[{"role": "user", "content": cau_hoi_nguoi_dung}]
)
# Request sau có thể được giảm chi phí cho phần cache nếu đạt điều kiện của nhà cung cấp;
# kiểm tra thời hạn, ngưỡng token và giá hiện hành trong tài liệu chính thức.

Chọn đúng mô hình cho đúng việc

Chiến lượcMô tả
Model RoutingDùng mô hình NHỎ/rẻ cho câu hỏi đơn giản, chỉ gọi mô hình lớn/đắt cho tác vụ thực sự phức tạp
Giới hạn max_tokens hợp lýKhông đặt max_tokens quá cao nếu câu trả lời thường ngắn — tránh lãng phí
Rút gọn lịch sử hội thoạiChỉ giữ N lượt gần nhất (đã nhắc ở chương 15), hoặc tóm tắt lịch sử cũ thay vì giữ nguyên văn
Batch ProcessingVới tác vụ KHÔNG cần phản hồi tức thời, dùng Batch API (thường rẻ hơn đáng kể) thay vì gọi real-time

Đo tốc độ đầu-cuối, không chỉ thời gian model

Theo dõi riêng time-to-first-token, thời gian hoàn tất, token/giây, tỷ lệ timeout/lỗi và chi phí trên mỗi tác vụ thành công. Tổng thời gian còn gồm retrieval, tool, mạng và hàng đợi. So sánh model routing/caching bằng cùng tập request đại diện; tính cả chi phí judge, retry và request thất bại. Không cache dữ liệu nhạy cảm nếu chính sách lưu trữ không cho phép.

Quan trọng
Luôn đo lường trước khi tối ưu — theo dõi chi phí thực tế theo từng loại request (dùng ID/tag phân loại), xác định đúng phần nào đang tốn kém nhất trước khi quyết định tối ưu, tránh tối ưu "cảm tính" vào chỗ không thực sự ảnh hưởng nhiều.
