10 Case Study: Thiết kế URL Shortener

Áp dụng toàn bộ kiến thức đã học vào một bài toán System Design kinh điển — dạng câu hỏi phổ biến nhất trong phỏng vấn.

Bước 1: Làm rõ yêu cầu (Requirements)

  • Chức năng: Rút gọn URL dài thành URL ngắn; khi truy cập URL ngắn, chuyển hướng (redirect) tới URL gốc
  • Quy mô ước tính: 100 triệu URL mới/tháng, tỉ lệ đọc:ghi khoảng 100:1 (đọc/redirect nhiều hơn tạo mới rất nhiều)

Bước 2: Thiết kế API cơ bản

api_design.txt

  Input:  { "url_goc": "https://example.com/bai-viet-rat-dai..." }
  Output: { "url_ngan": "https://sho.rt/aZ3kP9" }

GET /aZ3kP9
  -> HTTP 302 Redirect tới url_goc tương ứng

Bước 3: Thuật toán sinh mã rút gọn

Dùng Base62 (chữ a-z, A-Z, số 0-9 = 62 ký tự) encode một ID số nguyên tăng dần — với 6 ký tự, có thể tạo 62⁶ ≈ 56 tỷ mã khác nhau, thừa sức cho hàng trăm triệu URL.

base62_concept.py 
BANG_KY_TU = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def ma_hoa_base62(so_id):
    if so_id == 0:
        return BANG_KY_TU[0]
    ket_qua = ""
    while so_id > 0:
        ket_qua = BANG_KY_TU[so_id % 62] + ket_qua
        so_id //= 62
    return ket_qua

print(ma_hoa_base62(125_000_000))   # ví dụ: "8M0T"

Bước 4: Áp dụng toàn bộ kiến thức đã học

Kỹ thuật (đã học ở chương nào)Áp dụng vào bài toán
Caching (ch.4)Cache các URL được truy cập nhiều nhất trong Redis — vì tỉ lệ đọc:ghi rất cao (100:1)
Database Replication (ch.5)Nhiều Replica phục vụ ĐỌC (redirect) song song, giảm tải cho Primary
Load Balancing (ch.3)Phân phối hàng triệu request redirect/giây qua nhiều server
Horizontal Scaling (ch.2)Thêm server khi lượng truy cập tăng, vì service này có thể thiết kế stateless
Mẹo — Tư duy trả lời phỏng vấn System Design
Không có "đáp án đúng duy nhất" cho câu hỏi này — điều người phỏng vấn đánh giá là khả năng bạn đặt câu hỏi làm rõ yêu cầu, ước tính quy mô, và giải thích ĐÁNH ĐỔI của từng quyết định thiết kế (VD: "tại sao chọn cache thay vì tính toán lại mỗi lần"), không phải việc nhớ đúng một kiến trúc mẫu.
