Kết nối Node.js với MySQL

Xây REST API sản phẩm bằng Express 5 và mysql2: kiểm tra dữ liệu, truy vấn tham số và xử lý lỗi HTTP.

Làm quiz ở trang riêng

1. Mục tiêu học

Sau bài này, bạn giải thích được đường đi của một request HTTP từ Express tới MySQL, viết API đọc và tạo sản phẩm, kiểm tra đầu vào và trả lỗi JSON có chủ đích. Điều kiện trước: đã biết Promise, async/await, Express cơ bản và SQL ở hai chương trước. Nếu chưa vững, đọc lại Express cơ bản và REST API & Middleware.

Môi trường của ví dụ: Node.js 24.x, Express 5.x, mysql2 3.x, MySQL Server 8.4; mã CommonJS dùng đuôi .cjs. Đây là phạm vi phiên bản của bài, không phải tuyên bố phiên bản mới nhất. Xem tài liệu chính thức cuối bài trước khi đổi major version. Không cần cài các thư viện này để đọc Synaptrail.

Phạm vi kiểm chứng

Bản mẫu đã kiểm tra cú pháp và logic bằng test double (đối tượng giả thay Express/database). Chưa chạy tích hợp Express/mysql2 với MySQL thật vì môi trường kiểm thử chưa có các package và Docker Engine không hoạt động. Các kết quả HTTP dưới đây là kết quả kỳ vọng để bạn tự kiểm chứng, không phải log chạy database thật.

2. Vấn đề thực tế

Một trang bán hàng cần giữ sản phẩm sau khi tắt trình duyệt. Mảng JavaScript trong server mất khi tiến trình dừng; localStorage chỉ thuộc trình duyệt. Ta dùng MySQL lưu dữ liệu và Node.js làm nơi xử lý truy cập. Trình duyệt không giữ mật khẩu MySQL, không kết nối database trực tiếp. Ví dụ chỉ mở tại máy cá nhân, chưa có đăng nhập/phân quyền và chưa phù hợp đưa công khai.

Luồng tạo sản phẩm: client gửi JSON → Express đọc body → kiểm tra tên/giá → mysql2 gửi câu SQL và giá trị riêng → MySQL ghi hàng → server nhận ID → trả HTTP 201. Luồng đọc không ghi dữ liệu: SELECT lấy hàng và trả HTTP 200. Viết API ở đây là bài tập riêng; không biến website Synaptrail thành một backend đang vận hành.

3. Lý thuyết nền

API (Application Programming Interface) là giao diện để chương trình trao đổi dữ liệu. HTTP là giao thức trao đổi request (yêu cầu) và response (phản hồi). Trong bài, REST API tổ chức đường dẫn quanh tài nguyên sản phẩm và dùng GET/POST cùng status để diễn đạt thao tác và kết quả.

Connection pool và truy vấn bất đồng bộ

Connection pool là nhóm kết nối được tái sử dụng. Tạo pool một lần khi khởi động thay vì mỗi request tạo một kết nối mới. Với mysql2/promise, await pool.execute(...) trả một mảng: phần tử đầu là dữ liệu hàng khi SELECT, hoặc thông tin ghi như insertId khi INSERT. Pool giúp quản lý tài nguyên, không tự làm mọi truy vấn nhanh hoặc an toàn.

Parameter binding và prepared statement

Cả query(sql, values) và execute(sql, values) có thể nhận giá trị riêng, nhưng không nên gọi mọi dấu ? là server-side prepared statement. MySQL2 cung cấp execute() để prepare rồi execute trên server và tái sử dụng statement theo kết nối. Bài này dùng execute để minh họa đúng cơ chế. Không nối input vào SQL; placeholder dành cho giá trị, không thay tên bảng, cột hoặc từ khóa ORDER BY. Chọn identifier từ danh sách cố định nếu sau này cần sắp xếp động.

Prepared statement không thay validation, phân quyền hay giới hạn kết quả. Tên chứa dấu nháy vẫn là dữ liệu hợp lệ; giá sai kiểu vẫn phải từ chối. Ví dụ dùng giá nguyên theo đồng Việt Nam trong khoảng 0 đến 1.000.000.000; không dùng số thực để biểu diễn tiền lẻ. Tên được trim và giới hạn 100 Unicode code point để phù hợp cột VARCHAR(100) với utf8mb4.

Hợp đồng API nhỏ

RequestThành côngTrường hợp lỗi
GET /api/san-pham200, mảng tối đa 50 sản phẩm mới nhất500 hoặc 503 khi xử lý/database lỗi
GET /api/san-pham/:id200, đối tượng id/ten/gia400 khi ID sai; 404 khi ID đúng định dạng nhưng không có hàng
POST /api/san-pham201, đối tượng vừa tạo và header Location400 JSON/đầu vào sai; 413 body quá lớn; 415 không phải application/json

Mã 503 dành cho một số lỗi kết nối đã nhận diện; lỗi bất ngờ khác trả 500. Không gửi câu SQL, mật khẩu hoặc stack trace cho client. GET danh sách giới hạn 50 để tránh trả toàn bộ bảng; đây chưa phải phân trang. POST chưa có chống gửi trùng: chạy lại có thể tạo thêm sản phẩm cùng tên, không có bảo đảm idempotency.

4. Ví dụ hoàn chỉnh và giải thích

Bước 1 — chuẩn bị dự án thực hành riêng

Tạo thư mục api-san-pham-mau ngoài repo Synaptrail, mở terminal tại đó. Các lệnh sau là hướng dẫn cho người học, không phải yêu cầu thay package.json của website. Cần có Node.js 24 và MySQL 8.4 đang chạy, SQL client như mysql hoặc Workbench. Bài không tự cài hay bật dịch vụ.

Terminal trong thư mục thực hành
npm init -y
npm install express@5 mysql2@3
node --version
npm ls express mysql2

Lệnh cài đặt chọn major version của bài; phiên bản patch thực tế ghi trong package-lock.json. Giữ lockfile của dự án thực hành, không commit node_modules, .env hoặc thông tin đăng nhập. Ghi phiên bản thực tế vào báo cáo của bạn thay vì giả định cùng patch với tác giả.

Bước 2 — tạo schema thử riêng

Trong SQL client, dùng tài khoản có quyền tạo database để chạy schema.sql bên dưới. Chọn database mới cho bài, không trỏ vào dữ liệu thật. Nếu tên đã tồn tại, dừng và chọn tên mới rồi đổi DB_NAME; không dùng DROP để làm lại. Quản trị viên cần tạo/cấp cho tài khoản ứng dụng quyền SELECT và INSERT trên database mẫu; API không dùng root, không cần quyền CREATE/DROP khi chạy.

schema.sql — chạy trong SQL client
CREATE DATABASE synaptrail_api_mau CHARACTER SET utf8mb4;
USE synaptrail_api_mau;

CREATE TABLE san_pham (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  ten VARCHAR(100) NOT NULL,
  gia INT UNSIGNED NOT NULL,
  CONSTRAINT ck_ten CHECK (CHAR_LENGTH(TRIM(ten)) >= 1),
  CONSTRAINT ck_gia CHECK (gia <= 1000000000)
);

Khóa chính tự tăng tạo ID để client tham chiếu. NOT NULL, kiểu UNSIGNED và CHECK là lớp ràng buộc dữ liệu tại database; validation Node.js giúp phản hồi dễ hiểu trước khi gửi SQL. Cấu hình client dùng utf8mb4 để tên tiếng Việt và emoji không bị mất ký tự. Ví dụ giả định MySQL ở cổng 3306; nếu máy bạn dùng cổng khác, đổi trường port trong pool theo cấu hình thật.

Bước 3 — cấu hình môi trường, không đặt bí mật vào code

Tạo file .env tại thư mục thực hành với DB_HOST=127.0.0.1, DB_NAME=synaptrail_api_mau, DB_USER là tài khoản ứng dụng đã được cấp quyền, DB_PASSWORD là mật khẩu local của chính bạn. Không gửi giá trị thật qua chat hoặc đưa vào repo. Có thể thêm .env và node_modules/ vào .gitignore của dự án thực hành. Chạy Node với --env-file=.env để đọc các biến này; không cần thêm dotenv. Thiếu file hay biến bắt buộc phải được sửa tại máy, không thay bằng thông tin đăng nhập hard-code.

Bước 4 — API trong một file để quan sát toàn bộ luồng

Lưu nguyên khối dưới đây thành app.cjs. Số endpoint và trường dữ liệu được giữ ít để bạn tập trung vào request, SQL và phản hồi.

app.cjs
'use strict';
const express = require('express');
const mysql = require('mysql2/promise');

for (const name of ['DB_HOST', 'DB_USER', 'DB_PASSWORD', 'DB_NAME']) {
  if (!process.env[name]) throw new Error(`Thiếu biến môi trường ${name}`);
}
const pool = mysql.createPool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  port: 3306,
  charset: 'utf8mb4',
  waitForConnections: true,
  connectionLimit: 5,
  queueLimit: 20,
  connectTimeout: 5000,
});
const app = express();
app.use(express.json({ limit: '16kb' }));

function validateProduct(body) {
  if (!body || typeof body !== 'object' || Array.isArray(body)) return null;
  if (typeof body.ten !== 'string') return null;
  const ten = body.ten.trim();
  const gia = body.gia;
  if ([...ten].length < 1 || [...ten].length > 100) return null;
  if (!Number.isSafeInteger(gia) || gia < 0 || gia > 1000000000) return null;
  return { ten, gia };
}

app.get('/api/san-pham', async (_req, res) => {
  const [rows] = await pool.execute(
    'SELECT id, ten, gia FROM san_pham ORDER BY id DESC LIMIT 50'
  );
  res.json(rows);
});

app.get('/api/san-pham/:id', async (req, res) => {
  const id = req.params.id;
  if (!/^[1-9]\d{0,9}$/.test(id) || Number(id) > 4294967295) {
    return res.status(400).json({ error: 'INVALID_ID' });
  }
  const [rows] = await pool.execute(
    'SELECT id, ten, gia FROM san_pham WHERE id = ?', [Number(id)]
  );
  if (rows.length === 0) return res.status(404).json({ error: 'NOT_FOUND' });
  res.json(rows[0]);
});

app.post('/api/san-pham', async (req, res) => {
  if (!req.is('application/json')) {
    return res.status(415).json({ error: 'JSON_REQUIRED' });
  }
  const product = validateProduct(req.body);
  if (!product) return res.status(400).json({ error: 'INVALID_PRODUCT' });
  const [result] = await pool.execute(
    'INSERT INTO san_pham (ten, gia) VALUES (?, ?)',
    [product.ten, product.gia]
  );
  res.location(`/api/san-pham/${result.insertId}`).status(201).json({
    id: result.insertId, ...product,
  });
});

app.use((_req, res) => res.status(404).json({ error: 'ROUTE_NOT_FOUND' }));
app.use((err, _req, res, _next) => {
  if (err.type === 'entity.parse.failed') {
    return res.status(400).json({ error: 'INVALID_JSON' });
  }
  if (err.type === 'entity.too.large') {
    return res.status(413).json({ error: 'BODY_TOO_LARGE' });
  }
  console.error('API thất bại:', err.code || err.name);
  const unavailable = ['ECONNREFUSED', 'ETIMEDOUT', 'PROTOCOL_CONNECTION_LOST']
    .includes(err.code);
  res.status(unavailable ? 503 : 500).json({
    error: unavailable ? 'DATABASE_UNAVAILABLE' : 'INTERNAL_ERROR',
  });
});

async function start() {
  try {
    await pool.execute('SELECT 1');
    const server = app.listen(3000, '127.0.0.1', (error) => {
      if (error) return; // The server error listener below handles startup failure.
      console.log('API: http://127.0.0.1:3000/api/san-pham');
    });
    server.on('error', async (err) => {
      console.error('Không mở được server:', err.code || err.name);
      await pool.end();
      process.exitCode = 1;
    });
  } catch (err) {
    console.error('Không kết nối được database:', err.code || err.name);
    await pool.end();
    process.exitCode = 1;
  }
}
if (require.main === module) start();
module.exports = { app, pool, validateProduct };

Giải thích từng đoạn quan trọng

  1. require('express') và require('mysql2/promise') nạp HTTP framework và driver Promise. Vòng for kiểm biến cấu hình trước khi tạo pool; thông báo chỉ nêu tên biến thiếu.
  2. createPool tái sử dụng tối đa 5 kết nối, giới hạn hàng chờ 20 và thời gian thiết lập kết nối 5 giây. connectTimeout không phải thời gian tối đa cho mọi truy vấn SQL. Không gọi pool.end sau mỗi request.
  3. express.json đọc JSON với giới hạn 16 KB. validateProduct chỉ lấy ten và gia; trim tên, đếm code point và kiểm số nguyên an toàn. Giá dạng chuỗi như "250000" không được tự ép kiểu. Trường thừa được bỏ qua, không ghép vào SQL.
  4. GET danh sách trả mảng; GET chi tiết kiểm ID nguyên dương trong miền INT UNSIGNED rồi truyền ID qua placeholder. Mảng rỗng ở GET chi tiết dẫn tới 404, không phải lỗi kết nối.
  5. POST kiểm Content-Type trước khi dùng body. Khi validation sai, return kết thúc handler và chưa gọi INSERT. Khi đúng, tên và giá nằm trong mảng tham số, tách khỏi cấu trúc SQL; insertId tạo Location và nội dung HTTP 201.
  6. Handler async dùng await. Trong Express 5, Promise reject được chuyển tới error middleware; middleware lỗi có bốn tham số, kể cả _next không sử dụng. Các lỗi parser trả mã riêng; lỗi khác chỉ log mã/tên lỗi, không log body hoặc mật khẩu.
  7. start thử SELECT 1 trước khi listen; lỗi database thì đóng pool và đặt exitCode=1. Server chỉ bind 127.0.0.1:3000. Callback listen của Express 5 có thể nhận lỗi; kiểm error trước khi in thông báo thành công, còn listener error bên dưới đóng pool khi mở cổng thất bại. Điều kiện require.main giúp file không tự mở cổng khi được nạp bởi công cụ kiểm tra.
Khởi động, dừng bằng Ctrl+C trong đúng terminal
node --env-file=.env app.cjs

Khi kết nối thành công, thông báo kỳ vọng là API: http://127.0.0.1:3000/api/san-pham. Nếu bảng mới chưa có dữ liệu, mở endpoint danh sách sẽ nhận []. Mẫu này chưa có cơ chế graceful shutdown cho triển khai production; Ctrl+C kết thúc tiến trình thực hành.

Bước 5 — gửi request bằng Node, tránh khác biệt cú pháp curl trên Windows

Mở terminal thứ hai cùng thư mục, lưu thu-api.cjs rồi chạy node thu-api.cjs. Chương trình dùng fetch có sẵn ở phiên bản Node của bài. Mỗi lần chạy sẽ tạo thêm một hàng trong database thử.

thu-api.cjs
'use strict';
async function main() {
  const base = 'http://127.0.0.1:3000/api/san-pham';
  const created = await fetch(base, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ ten: 'Bàn phím', gia: 250000 }),
  });
  if (created.status !== 201) throw new Error(`POST trả ${created.status}`);
  const product = await created.json();
  console.log('POST', created.status, product);
  const detail = await fetch(`${base}/${product.id}`);
  console.log('GET chi tiết', detail.status, await detail.json());
  const invalid = await fetch(base, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ ten: 'Bàn phím', gia: '250000' }),
  });
  console.log('POST sai kiểu', invalid.status, await invalid.json());
}
main().catch(error => { console.error(error.message); process.exitCode = 1; });

Kỳ vọng: dòng POST có status 201 và id do MySQL cấp; GET chi tiết có status 200 và cùng sản phẩm; POST giá chuỗi trả 400 với INVALID_PRODUCT. Không cố định ID bằng 1 vì auto-increment phụ thuộc dữ liệu đã ghi. Sau khi dừng và mở lại API, GET vẫn tìm được ID đó nếu MySQL giữ nguyên database.

5. Lỗi thường gặp và cách phân biệt

  • ECONNREFUSED: kiểm MySQL có chạy, host/port có đúng; không liên tục tạo tài khoản hoặc tắt kiểm soát truy cập để chữa lỗi.
  • Access denied hoặc unknown database: đối chiếu biến môi trường, quyền và tên database mẫu. Quyền CREATE của người chuẩn bị schema khác quyền SELECT/INSERT của API.
  • req.body không có dữ liệu: kiểm middleware JSON và header Content-Type; form gửi lên không tự biến thành JSON. Body JSON sai cú pháp trả 400; quá 16 KB trả 413.
  • Chấm điểm HTTP nhầm: ID abc là 400; ID hợp lệ không tìm thấy là 404; không trả 200 cho mọi lỗi. Không trả err.message trực tiếp ra client.
  • Nhầm execute với validation: tham số SQL không bảo đảm tên không rỗng hoặc giá có kiểu đúng. Cả hai lớp đều cần; không dùng placeholder thay tên bảng.
  • POST hai lần có hai hàng: đây là hành vi của mẫu, không phải bằng chứng request bị xử lý sai. Chống gửi trùng cần thiết kế riêng khi nghiệp vụ yêu cầu.

6. Bài tập ba mức

Dễ — quan sát HTTP và validation

Thử tên chỉ có khoảng trắng, tên 101 ký tự, giá -1, giá "1000" và giá 0. Ghi status/body và số lần INSERT; bốn đầu vào đầu phải bị từ chối trước database, giá 0 hợp lệ. Thử ID abc và một ID hợp lệ chắc chắn chưa có. Lưu kết quả thực thay vì chép kết quả kỳ vọng.

Vừa — chứng minh lưu bền

Tạo ba sản phẩm ở database thử, lưu ID, dừng/mở lại tiến trình Node và đọc lại từng ID. Xác nhận dữ liệu còn khi chỉ Node khởi động lại; phân biệt việc xóa database với khởi động lại API. Tên có dấu nháy phải được lưu như văn bản, không làm thay đổi cấu trúc SQL. Không thử trên dữ liệu thật.

Khó — kiểm đường lỗi có kiểm soát

Trên môi trường thử của riêng bạn, cấu hình một cổng MySQL không có dịch vụ để quan sát khởi động thất bại; khôi phục cấu hình rồi chạy lại. Gửi JSON hỏng/quá dung lượng và đường dẫn không tồn tại; lập bảng kỳ vọng/thực tế cho 400, 413, 415, 404. Viết test handler với pool giả và ghi rõ test đó chưa thay thế chạy Express/MySQL thật. Không tự dừng database được người khác sử dụng.

7. Tóm tắt

Pool được tạo một lần, SQL cố định và giá trị được bind qua execute. Validation quyết định dữ liệu hợp lệ; HTTP status thể hiện kết quả; database giữ dữ liệu ngoài vòng đời Node. Mẫu chưa có tài khoản/phân quyền, chống gửi trùng hoặc vận hành production; không public API ghi dữ liệu trước khi thiết kế và kiểm thử những phần đó. ORM ở khóa riêng là bước tiếp theo, không phải lý do bỏ qua SQL và hợp đồng HTTP.
