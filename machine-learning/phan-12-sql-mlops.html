================================================================ CHƯƠNG 38: SQL CHO ML ================================================================

38.1. Vì sao Data Scientist/ML Engineer cần SQL?

Dữ liệu doanh nghiệp hiếm khi nằm sẵn trong file CSV gọn gàng — nó thường nằm rải rác trong các cơ sở dữ liệu quan hệ (MySQL, PostgreSQL, SQL Server...), với hàng chục bảng liên kết với nhau. SQL (Structured Query Language) là ngôn ngữ chuẩn để truy vấn, lọc, và tổng hợp dữ liệu trực tiếp từ những cơ sở dữ liệu này trước khi đưa vào Pandas (Chương 5).

38.2. Các câu lệnh SQL cốt lõi

sql 
-- Lấy các cột cần thiết, lọc điều kiện
SELECT ten_khach_hang, tuoi, tong_chi_tieu
FROM khach_hang
WHERE tuoi >= 18 AND tong_chi_tieu > 1000000;

-- Nhóm và tổng hợp - giống groupby() của Pandas (Chương 5)
SELECT thanh_pho, AVG(tong_chi_tieu) AS chi_tieu_trung_binh, COUNT(*) AS so_khach_hang
FROM khach_hang
GROUP BY thanh_pho
ORDER BY chi_tieu_trung_binh DESC;

-- JOIN: kết hợp dữ liệu từ nhiều bảng - bước rất phổ biến khi chuẩn bị dữ liệu ML
SELECT k.ten_khach_hang, k.tuoi, d.san_pham, d.ngay_mua
FROM khach_hang k
JOIN don_hang d ON k.id = d.khach_hang_id
WHERE d.ngay_mua >= '2025-01-01';
Câu lệnh SQLTương đương trong Pandas (Chương 5)
SELECT cot1, cot2df[['cot1', 'cot2']]
WHERE dieu_kiendf[df['cot'] > gia_tri]
GROUP BY ... AVG(...)df.groupby('cot')['gia_tri'].mean()
JOINpd.merge(df1, df2, on='khoa_chung')
ORDER BYdf.sort_values('cot')
💡 Mẹo ghi nhớ
Nếu đã thành thạo Pandas (Chương 5), học SQL sẽ nhanh hơn nhiều — hầu hết thao tác đều có "bản dịch" tương ứng. Sự khác biệt lớn nhất: SQL thao tác trực tiếp trên dữ liệu nằm trong database (có thể hàng tỷ dòng), trong khi Pandas thao tác trên dữ liệu đã nạp vào bộ nhớ RAM.

38.2b. Window Functions — tính toán theo nhóm mà không "gộp mất" từng dòng

GROUP BY ở trên có một hạn chế: kết quả bị "gộp" thành 1 dòng cho mỗi nhóm, mất đi thông tin từng dòng gốc. Window Function giải quyết vấn đề này: tính toán tổng hợp theo nhóm (OVER (PARTITION BY ...)) nhưng vẫn giữ nguyên từng dòng dữ liệu gốc — cực kỳ hữu ích khi chuẩn bị đặc trưng (feature engineering — Chương 16) cho ML.

sql 
-- Xếp hạng chi tiêu của từng khách hàng NGAY TRONG thành phố của họ
-- (khác GROUP BY: vẫn giữ nguyên từng dòng khách hàng, không gộp mất)
SELECT
    ten_khach_hang,
    thanh_pho,
    tong_chi_tieu,
    RANK() OVER (PARTITION BY thanh_pho ORDER BY tong_chi_tieu DESC) AS xep_hang_trong_thanh_pho,
    AVG(tong_chi_tieu) OVER (PARTITION BY thanh_pho) AS chi_tieu_tb_thanh_pho,
    tong_chi_tieu - AVG(tong_chi_tieu) OVER (PARTITION BY thanh_pho) AS chenh_lech_so_voi_tb
FROM khach_hang;
📌 Ứng dụng thực tế cho Feature Engineering (Chương 16)
Cột chenh_lech_so_voi_tb ở trên — "khách hàng này chi tiêu nhiều/ít hơn trung bình thành phố bao nhiêu" — chính xác là dạng đặc trưng "tổng hợp theo nhóm" đã học ở Chương 16, nhưng giờ được tính ngay trong SQL trước khi dữ liệu được đưa vào Python — giúp giảm tải xử lý phía Pandas khi làm việc với dữ liệu lớn nằm trong database.

38.3. Kết nối SQL với Python

python 
import sqlite3
import pandas as pd

# Kết nối tới cơ sở dữ liệu SQLite (file nhẹ, phù hợp để học/thử nghiệm)
ket_noi = sqlite3.connect('du_lieu_ban_hang.db')

# Chạy trực tiếp câu truy vấn SQL và nhận kết quả dưới dạng DataFrame
truy_van = """
    SELECT thanh_pho, AVG(tong_chi_tieu) AS chi_tieu_tb
    FROM khach_hang
    GROUP BY thanh_pho
"""
df = pd.read_sql(truy_van, ket_noi)
print(df.head())

ket_noi.close()
  1. sqlite3.connect(...) — mở kết nối tới cơ sở dữ liệu; với các hệ quản trị khác (PostgreSQL, MySQL) thường dùng thư viện sqlalchemy để kết nối tương tự.
  2. pd.read_sql(truy_van, ket_noi) — hàm cực kỳ hữu ích: chạy câu SQL và trả kết quả thẳng thành DataFrame, sẵn sàng cho các bước tiền xử lý ở Chương 4-5, 13-17.
  3. ket_noi.close() — luôn đóng kết nối sau khi dùng xong để giải phóng tài nguyên.
⚠️ Lưu ý hiệu năng
Với dữ liệu lớn, nên lọc/tổng hợp càng nhiều càng tốt ngay trong câu SQL (dùng WHERE, GROUP BY) thay vì kéo toàn bộ bảng thô về rồi mới lọc bằng Pandas — giảm tải cho cả mạng lẫn bộ nhớ RAM của máy chạy Python.

Bài tập thực hành

Bài 1

Viết câu SQL lấy ra top 5 sản phẩm bán chạy nhất (theo số lượng đơn hàng) từ bảng don_hang có cột san_pham.

sql 
SELECT san_pham, COUNT(*) AS so_don_hang
FROM don_hang
GROUP BY san_pham
ORDER BY so_don_hang DESC
LIMIT 5;
❌ Lỗi thường gặp: Kéo toàn bộ bảng hàng triệu dòng về Python rồi mới lọc, gây tràn bộ nhớ hoặc chậm không cần thiết.
✅ Best Practice: Luôn tối ưu câu SQL để trả về đúng dữ liệu cần thiết, tận dụng sức mạnh xử lý của database engine.

🎯 Tổng kết Chương 38

  • SQL là ngôn ngữ chuẩn để truy vấn dữ liệu từ cơ sở dữ liệu quan hệ trước khi đưa vào Pandas.
  • Các thao tác SQL cốt lõi (SELECT, WHERE, GROUP BY, JOIN) đều có "bản dịch" tương ứng trong Pandas.
  • Window Function (OVER PARTITION BY) tính toán theo nhóm mà vẫn giữ nguyên từng dòng — hữu ích cho feature engineering ngay trong SQL.
  • pd.read_sql() là cầu nối tiện lợi nhất giữa SQL và hệ sinh thái Python.
================================================================ CHƯƠNG 39: MLOPS & MLFLOW ================================================================

39.1. MLOps là gì?

MLOps (Machine Learning Operations) là tập hợp thực hành kết hợp ML, DevOps và Data Engineering để xây dựng, triển khai và vận hành mô hình ML một cách đáng tin cậy và có thể lặp lại — mở rộng những gì đã học ở Chương 36-37 (deploy, Docker, Git) thành một quy trình toàn diện hơn.

🔴 Vấn đề MLOps giải quyết
Sau vài chục lần thử nghiệm với các thuật toán khác nhau (Phần 6-9) và các bộ siêu tham số khác nhau (Chương 34), rất dễ quên mất cấu hình nào cho kết quả tốt nhất, hoặc không thể tái lập chính xác một kết quả cũ. MLOps — cụ thể là experiment tracking — giải quyết đúng vấn đề này.

39.2. MLflow Tracking — ghi lại mọi thí nghiệm tự động

python 
# pip install mlflow
import mlflow
import mlflow.sklearn
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split
from sklearn.metrics import f1_score
from sklearn.datasets import make_classification

X, y = make_classification(n_samples=500, random_state=1)
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=1)

mlflow.set_experiment("du_doan_khach_hang_roi_bo")

# Thử nghiệm nhiều cấu hình, mỗi lần chạy được ghi lại tự động
for n_est in [50, 100, 200]:
    with mlflow.start_run():
        model = RandomForestClassifier(n_estimators=n_est, random_state=1)
        model.fit(X_train, y_train)
        f1 = f1_score(y_test, model.predict(X_test))

        # Ghi lại siêu tham số, metric, và chính mô hình
        mlflow.log_param("n_estimators", n_est)
        mlflow.log_metric("f1_score", f1)
        mlflow.sklearn.log_model(model, "model")

        print(f"n_estimators={n_est}: F1={f1:.3f} (đã ghi vào MLflow)")

# Mở giao diện web để xem lại toàn bộ lịch sử thí nghiệm:
# mlflow ui
  1. mlflow.set_experiment(...) — đặt tên cho nhóm thí nghiệm, giúp tổ chức nhiều lần chạy liên quan tới cùng 1 bài toán.
  2. with mlflow.start_run(): — mỗi khối lệnh bên trong tương ứng với "1 lần chạy" (run) được ghi lại đầy đủ và độc lập.
  3. mlflow.log_param(...) / log_metric(...) — ghi lại siêu tham số đầu vào và kết quả đánh giá tương ứng, cho phép so sánh giữa các lần chạy sau này.
  4. mlflow.sklearn.log_model(model, "model") — lưu lại chính mô hình đã huấn luyện, kèm theo mọi thông tin cấu hình — thay thế cách lưu thủ công bằng joblib ở Chương 36, nhưng có thêm khả năng truy vết lịch sử.
  5. mlflow ui — lệnh terminal mở giao diện web trực quan, cho phép so sánh mọi lần chạy qua bảng và biểu đồ mà không cần tự viết code so sánh thủ công.

39.3. Model Registry — quản lý vòng đời mô hình

Ngoài Tracking, MLflow còn có Model Registry — nơi quản lý các phiên bản mô hình theo trạng thái (ví dụ: Staging, Production, Archived), giúp team biết chính xác phiên bản nào đang chạy thật trong sản phẩm, tránh nhầm lẫn khi có nhiều mô hình được thử nghiệm song song.

Vòng đời một phiên bản mô hình trong Model Registry: từ thử nghiệm tới chính thức phục vụ người dùng thật.

Bài tập thực hành

Bài 1

Sửa vòng lặp ở mục 39.2 để thêm log thêm siêu tham số max_depth với các giá trị [5, 10, None], kết hợp với các giá trị n_estimators hiện có.

python 
for n_est in [50, 100, 200]:
    for depth in [5, 10, None]:
        with mlflow.start_run():
            model = RandomForestClassifier(n_estimators=n_est, max_depth=depth, random_state=1)
            model.fit(X_train, y_train)
            f1 = f1_score(y_test, model.predict(X_test))
            mlflow.log_param("n_estimators", n_est)
            mlflow.log_param("max_depth", depth)
            mlflow.log_metric("f1_score", f1)
❌ Lỗi thường gặp: Chỉ ghi chú kết quả thí nghiệm thủ công trong Excel/notebook, dễ nhầm lẫn hoặc mất mát khi số lượng thử nghiệm tăng lên.
✅ Best Practice: Tích hợp mlflow.start_run() ngay từ những thử nghiệm đầu tiên của dự án, không đợi tới khi có quá nhiều kết quả mới bắt đầu theo dõi.
🆕 Cập nhật 2026 — MLOps mở rộng thành LLMOps cho ứng dụng GenAI
Khi hệ thống dùng LLM (khóa AI Engineer) thay vì tự huấn luyện mô hình, các nguyên lý MLOps ở trên vẫn áp dụng, nhưng có thêm vài "đối tượng" mới cần theo dõi và quản lý phiên bản:
  • Prompt versioning: prompt/system prompt cũng cần theo dõi phiên bản như code — đổi một câu trong prompt có thể thay đổi hành vi cả hệ thống, tương tự đổi một siêu tham số (hyperparameter).
  • Đánh giá chất lượng (eval): thay vì chỉ đo accuracy/F1 (Chương 32) trên tập test cố định, ứng dụng LLM thường cần bộ câu hỏi/kịch bản mẫu (eval set) và có thể dùng chính một LLM khác để chấm điểm (LLM-as-judge).
  • Theo dõi chi phí & độ trễ theo token: tương tự theo dõi metric mô hình trong MLflow, nhưng chỉ số giờ là số token, chi phí API, và thời gian phản hồi theo từng phiên bản prompt/model.
  • Registry cho RAG: nếu dùng RAG (Chương 45), nguồn dữ liệu/vector database cũng cần versioning giống Model Registry — biết chính xác phiên bản dữ liệu nào đang được dùng để trả lời.
Tư duy cốt lõi không đổi: mọi thứ ảnh hưởng tới kết quả đầu ra (data, model, code, giờ thêm cả prompt) đều cần được theo dõi phiên bản và có thể tái lập lại được.

🎯 Tổng kết Chương 39

  • MLOps mở rộng thực hành DevOps cho vòng đời mô hình ML, từ thử nghiệm tới vận hành.
  • MLflow Tracking ghi lại tự động tham số, metric và mô hình của mỗi lần chạy, dễ dàng so sánh qua giao diện web.
  • Model Registry quản lý trạng thái phiên bản mô hình, tránh nhầm lẫn giữa thử nghiệm và production.
  • Với ứng dụng LLM/GenAI, MLOps mở rộng thành LLMOps: thêm versioning cho prompt và dữ liệu RAG, cùng theo dõi chi phí/chất lượng theo token.
🆕 Cập nhật 2026 — LLMOps: MLOps cho thời đại GenAI
Khi ứng dụng chuyển sang dùng LLM (khóa AI Engineer) thay vì chỉ mô hình Predictive AI truyền thống, các nguyên lý MLOps ở trên vẫn áp dụng nhưng cần thêm vài mảnh ghép mới — thường gọi chung là LLMOps:
  • Prompt versioning: theo dõi phiên bản prompt/system prompt giống như theo dõi phiên bản mô hình, vì thay đổi một câu chữ trong prompt có thể ảnh hưởng lớn tới chất lượng đầu ra.
  • Eval cho LLM: khác với accuracy/F1 (Chương 32) vốn có đáp án đúng rõ ràng, đánh giá chất lượng câu trả lời của LLM (mạch lạc, đúng ngữ cảnh, không hallucination) thường cần bộ test case mẫu, hoặc dùng chính một LLM khác để "chấm điểm" (LLM-as-judge).
  • Theo dõi chi phí token: khác với mô hình tự host (chi phí cố định theo hạ tầng), gọi API LLM tính phí theo số token — cần theo dõi sát để tránh chi phí vận hành tăng đột biến.
  • Tracing cho Agent (Chương 46): khi hệ thống có nhiều bước gọi tool/LLM nối tiếp nhau, cần công cụ "trace" toàn bộ chuỗi hành động để debug khi Agent trả lời sai hoặc chọn sai công cụ.
💡 Nhiều công cụ MLOps truyền thống (MLflow...) đã bổ sung tính năng LLMOps; đồng thời cũng xuất hiện các công cụ chuyên biệt riêng cho theo dõi/eval LLM. Nguyên lý cốt lõi ("đo lường, ghi lại, tái lập được") không đổi — chỉ mở rộng thêm đối tượng cần theo dõi.
================================================================ CHƯƠNG 40: DVC & KUBERNETES ================================================================

40.1. DVC (Data Version Control) — "Git cho dữ liệu"

Nhớ lại cảnh báo ở Chương 37: Git không phù hợp để lưu trực tiếp file dữ liệu/model lớn. DVC giải quyết vấn đề này: nó hoạt động song song với Git, nhưng lưu con trỏ (một file nhỏ, dạng text) trỏ tới dữ liệu thật đang nằm ở nơi lưu trữ riêng (local, S3, Google Drive...) — Git vẫn theo dõi lịch sử thay đổi, nhưng kho Git không hề phình to.

bash 
# Khởi tạo DVC trong dự án đã có Git
dvc init

# Bắt đầu theo dõi phiên bản một file dữ liệu lớn
dvc add data/du_lieu_khach_hang.csv
# Lệnh trên tạo ra file du_lieu_khach_hang.csv.dvc (con trỏ nhỏ, gọn)

# Commit CON TRỎ (không phải data thật) vào Git
git add data/du_lieu_khach_hang.csv.dvc .gitignore
git commit -m "Thêm phiên bản dữ liệu khách hàng v1"

# Đẩy dữ liệu thật lên nơi lưu trữ từ xa (remote storage)
dvc push

# Khi cần lấy lại đúng phiên bản dữ liệu tương ứng với 1 commit Git cũ:
git checkout 
dvc pull
  1. dvc add data/... — DVC tính toán "dấu vân tay" (hash) của file dữ liệu, tạo file .dvc nhỏ chứa thông tin đó, đồng thời tự thêm dữ liệu thật vào .gitignore.
  2. git commit ...file.dvc — Git chỉ theo dõi file con trỏ nhẹ, giữ lịch sử thay đổi dữ liệu mà không phình kho.
  3. dvc push / dvc pull — đồng bộ dữ liệu thật với kho lưu trữ từ xa, tương tự git push/git pull nhưng cho dữ liệu.
💡 Kết hợp DVC với MLflow
DVC trả lời câu hỏi "phiên bản dữ liệu nào đã dùng?", MLflow (Chương 39) trả lời câu hỏi "cấu hình/kết quả thí nghiệm nào?" — kết hợp cả hai cho khả năng tái lập hoàn toàn (full reproducibility) bất kỳ kết quả nào trong quá khứ: cùng dữ liệu, cùng code, cùng siêu tham số.

40.2. Kubernetes — mở rộng quy mô ứng dụng ML (giới thiệu)

Nhớ lại Docker ở Chương 37: đóng gói ứng dụng thành container chạy nhất quán mọi nơi. Nhưng khi có hàng nghìn request/giây gọi tới API dự đoán (Chương 36), một container đơn lẻ không đủ sức xử lý. Kubernetes (K8s) là hệ thống điều phối (orchestration) giúp tự động quản lý, mở rộng (scale), và duy trì hàng loạt container chạy song song.

Khái niệm KubernetesÝ nghĩa
PodĐơn vị nhỏ nhất, thường chứa 1 container (ví dụ: 1 instance API dự đoán từ Chương 36)
DeploymentĐịnh nghĩa "cần chạy bao nhiêu Pod giống nhau", tự động khởi động lại nếu Pod bị lỗi
ServiceĐịa chỉ ổn định để truy cập vào nhóm Pod, tự động phân phối tải (load balancing)
Horizontal Pod AutoscalerTự động tăng/giảm số lượng Pod theo tải thực tế (ví dụ CPU usage)
Service phân phối request tới nhiều Pod giống nhau — mỗi Pod chạy 1 instance API dự đoán, tăng khả năng chịu tải.
🔴 Đây chỉ là giới thiệu — Kubernetes là một chủ đề rất sâu
Kubernetes có đường cong học tập dốc và thường là công việc chuyên trách của MLOps Engineer/DevOps Engineer, không nhất thiết mọi Data Scientist đều cần thành thạo. Điều quan trọng ở giai đoạn này là hiểu khái niệm và vì sao nó cần thiết khi hệ thống ML mở rộng quy mô, để có thể giao tiếp hiệu quả với đội hạ tầng.

Bài tập thực hành

Bài 1

Giải thích bằng lời: nếu một Pod chạy API dự đoán bị crash (lỗi và dừng đột ngột), Kubernetes Deployment sẽ phản ứng như thế nào?

Deployment liên tục giám sát số lượng Pod đang chạy so với số lượng mong muốn đã khai báo. Nếu 1 Pod bị crash, Deployment sẽ tự động khởi động lại một Pod mới để thay thế, đảm bảo luôn duy trì đúng số lượng Pod đang hoạt động — đây là cơ chế "tự chữa lành" (self-healing) đặc trưng của Kubernetes.

❌ Lỗi thường gặp: Nhảy thẳng vào học Kubernetes chi tiết khi dự án còn nhỏ và chỉ có 1 người dùng — độ phức tạp thêm vào thường không đáng, hãy bắt đầu đơn giản với Docker trước.
✅ Best Practice: Dùng DVC song song với Git ngay từ đầu dự án có dữ liệu lớn, để đảm bảo khả năng tái lập kết quả về sau.

  • Kubernetes điều phối nhiều container để hệ thống ML chịu tải cao và tự phục hồi khi lỗi.
