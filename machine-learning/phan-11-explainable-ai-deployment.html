35.1. Vì sao cần "giải thích" mô hình?

Các mô hình mạnh nhất (Random Forest, Gradient Boosting, Neural Network) thường là "hộp đen" (black box) — chính xác cao nhưng khó hiểu tại sao ra kết quả đó, trái ngược với Decision Tree hay Linear Regression (dễ diễn giải nhưng thường kém chính xác hơn — nhắc lại đánh đổi ở Chương 24 và 20).

Lý do cần giải thíchVí dụ
Tuân thủ pháp lýLuật yêu cầu giải thích lý do từ chối khoản vay cho khách hàng
Debug mô hìnhPhát hiện mô hình đang dựa vào đặc trưng sai/thiên vị (bias)
Xây dựng niềm tinBác sĩ cần hiểu vì sao AI đề xuất một chẩn đoán trước khi tin tưởng
Cải thiện mô hìnhHiểu đặc trưng nào thực sự quan trọng để tập trung feature engineering

35.2. SHAP (SHapley Additive exPlanations)

SHAP dựa trên khái niệm Shapley Value từ lý thuyết trò chơi hợp tác: coi mỗi đặc trưng như một "người chơi" đóng góp vào kết quả dự đoán cuối cùng, và tính toán công bằng phần đóng góp của từng đặc trưng bằng cách xem xét mọi thứ tự kết hợp đặc trưng có thể.

+0.32
tuoi
+0.15
no_hien_tai
-0.22

+0.08
SHAP values cho 1 dự đoán cụ thể: thanh xanh đẩy dự đoán về phía "duyệt vay", thanh đỏ đẩy về phía "từ chối".
python 
# pip install shap
import shap
from sklearn.ensemble import RandomForestClassifier
from sklearn.datasets import load_breast_cancer

data = load_breast_cancer()
X, y = data.data, data.target
model = RandomForestClassifier(n_estimators=100, random_state=1).fit(X, y)

# TreeExplainer được tối ưu riêng cho các mô hình dựa trên cây (Random Forest, XGBoost...)
explainer = shap.TreeExplainer(model)
shap_values = explainer.shap_values(X)

# Giải thích TOÀN CỤC: đặc trưng nào quan trọng nhất trên toàn bộ dữ liệu
shap.summary_plot(shap_values[1], X, feature_names=data.feature_names)

# Giải thích CỤC BỘ: vì sao mô hình dự đoán như vậy cho MỘT mẫu cụ thể
mau_thu_0 = X[0:1]
shap.force_plot(explainer.expected_value[1], shap_values[1][0], mau_thu_0,
                 feature_names=data.feature_names)
  1. shap.TreeExplainer(model) — phiên bản SHAP tối ưu tốc độ cho các mô hình dựa trên cây quyết định (Random Forest, Gradient Boosting — Phần 7-8), nhanh hơn nhiều so với phương pháp SHAP tổng quát.
  2. shap.summary_plot(...) — biểu đồ giải thích toàn cục: tổng hợp mức độ ảnh hưởng của từng đặc trưng qua toàn bộ tập dữ liệu, tương tự Feature Importance ở Chương 27 nhưng chi tiết và có hướng (tăng/giảm) hơn.
  3. shap.force_plot(...) — biểu đồ giải thích cục bộ: cho một mẫu dữ liệu cụ thể, hiển thị chính xác đặc trưng nào đẩy dự đoán tăng/giảm và mức độ bao nhiêu.

35.3. LIME (Local Interpretable Model-agnostic Explanations)

Khác với SHAP (dựa trên nền tảng lý thuyết trò chơi chặt chẽ), LIME dùng ý tưởng đơn giản hơn: quanh 1 điểm dữ liệu cần giải thích, tạo ra nhiều mẫu nhiễu loạn nhỏ xung quanh nó, rồi huấn luyện một mô hình đơn giản, dễ diễn giải (như Linear Regression) chỉ trên vùng lân cận đó để xấp xỉ hành vi của mô hình phức tạp cục bộ.

Tiêu chíSHAPLIME
Nền tảng lý thuyếtShapley Value (lý thuyết trò chơi), có tính chất toán học chặt chẽXấp xỉ cục bộ bằng mô hình đơn giản, trực giác hơn
Tốc độNhanh với TreeExplainer, chậm hơn với mô hình khácThường nhanh, độc lập với loại mô hình
Tính nhất quánCó đảm bảo toán học về tính công bằng khi phân bổ đóng gópCó thể cho kết quả hơi khác nhau giữa các lần chạy do tính ngẫu nhiên
💡 "Model-agnostic" nghĩa là gì?
LIME (và SHAP ở chế độ tổng quát) được gọi là model-agnostic — không quan tâm mô hình bên trong là gì (Random Forest, Neural Network, hay bất kỳ thuật toán nào), miễn có hàm predict() là có thể giải thích được. Điều này khác với các phương pháp giải thích "tích hợp sẵn" chỉ áp dụng được cho 1 loại mô hình cụ thể.

35.4. Fairness & Bias Auditing — mô hình chính xác chưa chắc đã công bằng

SHAP/LIME giải thích vì sao mô hình dự đoán một kết quả, nhưng không tự động cho biết mô hình có đối xử công bằng giữa các nhóm người dùng khác nhau hay không. Một mô hình có Accuracy cao vẫn có thể học phải các thiên kiến (bias) có sẵn trong dữ liệu lịch sử — ví dụ mô hình duyệt vay từng huấn luyện trên dữ liệu quá khứ có thể vô tình học lại định kiến giới tính/chủng tộc từng tồn tại trong quyết định của con người.

Chỉ số FairnessCâu hỏi trả lời
Demographic ParityTỉ lệ được dự đoán "duyệt/tích cực" có bằng nhau giữa các nhóm không? (VD: nam vs nữ)
Equalized OddsTrong số những người thực sự đủ điều kiện (hoặc không), tỉ lệ True Positive Rate/False Positive Rate (Chương 32) có bằng nhau giữa các nhóm không?
Disparate Impact RatioTỉ lệ được duyệt của nhóm thiểu số so với nhóm đa số — theo quy tắc "80%" phổ biến trong luật lao động Mỹ, tỉ lệ này nên trên 0.8
python 
# pip install fairlearn
from fairlearn.metrics import MetricFrame, demographic_parity_difference
from sklearn.metrics import accuracy_score

# nhom_nhay_cam: cột giới tính/chủng tộc... KHÔNG dùng làm feature huấn luyện,
# nhưng vẫn cần giữ lại riêng để KIỂM TRA fairness sau khi có dự đoán
khung_metric = MetricFrame(
    metrics=accuracy_score,
    y_true=y_test,
    y_pred=y_pred,
    sensitive_features=nhom_nhay_cam
)
print(khung_metric.by_group)   # accuracy riêng cho từng nhóm - phát hiện chênh lệch bất thường

do_lech = demographic_parity_difference(y_test, y_pred, sensitive_features=nhom_nhay_cam)
print(f"Demographic Parity Difference: {do_lech:.3f}")   # càng gần 0 càng công bằng
🔴 Đánh đổi quan trọng: không có "công bằng tuyệt đối"
Về mặt toán học, đã chứng minh được rằng không thể đồng thời thỏa mãn tất cả định nghĩa fairness cùng lúc trừ trường hợp đặc biệt — tối ưu Demographic Parity có thể làm giảm Equalized Odds và ngược lại. Chọn chỉ số fairness nào để ưu tiên là một quyết định mang tính chính sách/đạo đức, không phải thuần túy kỹ thuật — nên luôn có sự tham gia của các bên liên quan (pháp lý, đạo đức, đối tượng bị ảnh hưởng), không để một mình đội kỹ thuật tự quyết định.

Bài tập thực hành

Bài 1

Giải thích bằng lời: nếu SHAP value của đặc trưng "no_hien_tai" là -0.22 cho một khách hàng cụ thể, điều đó có ý nghĩa gì đối với quyết định của mô hình?

Giá trị âm nghĩa là đặc trưng "nợ hiện tại" của khách hàng này đang kéo dự đoán về phía "từ chối vay" (giảm xác suất được duyệt), với mức độ đóng góp là 0.22 đơn vị trên thang xác suất/log-odds mà mô hình dùng. Nếu không có yếu tố này, dự đoán của mô hình cho khách hàng đó sẽ nghiêng về phía "duyệt vay" nhiều hơn.

❌ Lỗi thường gặp: Nhầm lẫn giữa giải thích toàn cục (feature importance chung) và giải thích cục bộ (vì sao 1 dự đoán cụ thể ra như vậy) — dùng sai loại cho câu hỏi cần trả lời.
✅ Best Practice: Dùng summary_plot để hiểu mô hình nói chung, dùng force_plot/LIME khi cần giải thích cho một khách hàng/trường hợp cụ thể.

🎯 Tổng kết Chương 35

  • Explainable AI giúp "mở hộp đen" của các mô hình phức tạp, cần thiết cho pháp lý, debug, và xây dựng niềm tin.
  • SHAP dựa trên Shapley Value, có nền tảng toán học chặt chẽ; LIME xấp xỉ cục bộ bằng mô hình đơn giản.
  • Cả hai đều là "model-agnostic" — hoạt động độc lập với loại mô hình bên trong.
  • Fairness Auditing (Demographic Parity, Equalized Odds) kiểm tra mô hình có đối xử công bằng giữa các nhóm — không thể tối ưu mọi định nghĩa fairness cùng lúc, đây là quyết định chính sách chứ không chỉ kỹ thuật.
================================================================ CHƯƠNG 36: MODEL DEPLOYMENT ================================================================

36.1. Từ notebook tới sản phẩm — có gì phải làm?

4 bước cơ bản đưa một mô hình từ notebook thành dịch vụ thực tế.

36.2. Bước 1: Lưu mô hình đã huấn luyện

python 
import joblib
from sklearn.ensemble import RandomForestClassifier
from sklearn.datasets import load_breast_cancer

X, y = load_breast_cancer(return_X_y=True)
model = RandomForestClassifier(n_estimators=100, random_state=1).fit(X, y)

# Lưu mô hình (và pipeline nếu có - Chương 18) ra file để dùng lại mà không cần huấn luyện lại
joblib.dump(model, 'model.pkl')

# Nạp lại mô hình ở bất kỳ đâu, bất kỳ lúc nào
model_da_luu = joblib.load('model.pkl')
print(model_da_luu.predict(X[:3]))
💡 Mẹo: luôn lưu cả Pipeline, không chỉ mô hình
Nếu dự án có bước tiền xử lý (Chương 13, 18), hãy lưu toàn bộ Pipeline (bao gồm scaler, encoder, model) chứ không chỉ riêng mô hình — đảm bảo dữ liệu mới trong production được xử lý giống hệt lúc huấn luyện.

36.3. Bước 2: Viết API với Flask

Flask là framework web Python nhẹ, phổ biến để nhanh chóng biến mô hình thành API.

python 
# app_flask.py
from flask import Flask, request, jsonify
import joblib
import numpy as np

app = Flask(__name__)
model = joblib.load('model.pkl')

@app.route('/predict', methods=['POST'])
def predict():
    du_lieu = request.get_json()          # nhận dữ liệu JSON từ client
    dac_trung = np.array(du_lieu['features']).reshape(1, -1)
    du_doan = model.predict(dac_trung)[0]
    xac_suat = model.predict_proba(dac_trung)[0].tolist()
    return jsonify({
        'du_doan': int(du_doan),
        'xac_suat': xac_suat
    })

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
  1. @app.route('/predict', methods=['POST']) — định nghĩa một "endpoint" API: khi có request POST tới địa chỉ /predict, hàm predict() sẽ được gọi.
  2. request.get_json() — lấy dữ liệu client gửi lên dưới dạng JSON, định dạng phổ biến nhất để trao đổi dữ liệu qua API.
  3. jsonify({...}) — trả kết quả về cho client dưới dạng JSON, dễ dàng tích hợp với web app, mobile app, hoặc hệ thống khác.

36.4. FastAPI — lựa chọn hiện đại hơn

FastAPI ngày càng phổ biến hơn Flask cho các dự án ML mới nhờ: tốc độ nhanh hơn, tự động sinh tài liệu API (Swagger UI), và validate dữ liệu đầu vào tự động bằng type hints Python.

python 
# app_fastapi.py
from fastapi import FastAPI
from pydantic import BaseModel
import joblib
import numpy as np

app = FastAPI()
model = joblib.load('model.pkl')

# Pydantic model định nghĩa CHÍNH XÁC cấu trúc dữ liệu đầu vào - tự động validate
class DauVao(BaseModel):
    features: list[float]

@app.post('/predict')
def predict(du_lieu: DauVao):
    dac_trung = np.array(du_lieu.features).reshape(1, -1)
    du_doan = model.predict(dac_trung)[0]
    xac_suat = model.predict_proba(dac_trung)[0].tolist()
    return {'du_doan': int(du_doan), 'xac_suat': xac_suat}

# Chạy bằng: uvicorn app_fastapi:app --reload --port 8000
# Tài liệu API tự động sinh tại: http://localhost:8000/docs

🆕 Cập nhật 2026 — Triển khai ứng dụng LLM/GenAI có gì khác?
Cách deploy ở trên (Flask/FastAPI + lưu model.pkl) áp dụng cho Predictive AI (Phần 1-12). Khi triển khai ứng dụng dựa trên LLM (khóa AI Engineer), có vài điểm khác biệt quan trọng cần biết thêm:
  • Không tự lưu "model.pkl": phần lớn ứng dụng gọi LLM qua API của nhà cung cấp (Anthropic, OpenAI...) thay vì tự host mô hình khổng lồ — endpoint FastAPI của bạn khi đó đóng vai trò "lớp trung gian" (gọi LLM, xử lý RAG, gọi tool) chứ không phải chính bản thân mô hình.
  • Streaming response: vì LLM sinh văn bản từng token một, API thường trả kết quả theo dạng streaming (trả dần từng phần) thay vì chờ toàn bộ câu trả lời xong mới trả một lần — giúp người dùng thấy phản hồi ngay lập tức thay vì chờ lâu.
  • Chi phí tính theo token: khác với model.pkl chạy miễn phí sau khi deploy, gọi LLM qua API tốn phí theo số token input/output — cần theo dõi chi phí (cost monitoring) như một chỉ số vận hành, tương tự theo dõi độ trễ (latency).
  • Health check phức tạp hơn: ngoài kiểm tra API còn sống, cần thêm giám sát riêng cho hallucination/chất lượng câu trả lời — thường qua việc chấm điểm mẫu output tự động (LLM-as-judge) hoặc phản hồi người dùng.
⚠️ Lưu ý khi triển khai thực tế
app.run() của Flask (hay chạy trực tiếp uvicorn) chỉ phù hợp để phát triển/thử nghiệm. Trong production thực tế, cần dùng WSGI/ASGI server chuyên dụng (như Gunicorn, Uvicorn với nhiều worker) đặt sau một reverse proxy (như Nginx) để đảm bảo hiệu năng và độ ổn định.

36.5. Model Drift — vì sao mô hình "tốt lúc deploy" có thể tệ dần theo thời gian?

Deploy xong không phải là kết thúc. Thế giới thực thay đổi liên tục — hành vi khách hàng, xu hướng thị trường, thậm chí cách người dùng viết văn bản — khiến dữ liệu mô hình gặp trong production ngày càng khác so với dữ liệu nó từng học. Hiện tượng này gọi là Model Drift, và nó khiến hiệu năng mô hình âm thầm giảm dần mà không có lỗi/crash nào báo hiệu.

Loại DriftĐiều gì thay đổiVí dụ
Data DriftPhân phối của input (đặc trưng đầu vào) thay đổiĐộ tuổi trung bình khách hàng dịch chuyển dần theo thời gian
Concept DriftMối quan hệ giữa input và target thay đổi, dù input trông vẫn "giống cũ"Hành vi gian lận thẻ tín dụng thay đổi thủ đoạn sau khi mô hình cũ được biết tới
🔴 Vì sao khó phát hiện bằng cách thông thường?
Khác với lỗi hệ thống (API crash, timeout) vốn dễ phát hiện qua health check (Chương 36.4), Model Drift không gây lỗi kỹ thuật nào cả — API vẫn trả lời bình thường, chỉ là câu trả lời ngày càng kém chính xác hơn. Cần đo lại các metric đã học ở Chương 32 (Accuracy, F1...) trên dữ liệu mới nhất, hoặc theo dõi phân phối input hiện tại có lệch nhiều so với phân phối dữ liệu train hay không — chứ không thể chỉ dựa vào việc "API không báo lỗi" để yên tâm.
📌 Cách xử lý thực tế
Giải pháp phổ biến nhất là huấn luyện lại định kỳ (retraining) trên dữ liệu mới, dùng chính hạ tầng MLOps đã học ở Phần 12 (MLflow Model Registry — Chương 39) để quản lý phiên bản mô hình mới mà không làm gián đoạn hệ thống đang chạy — thường qua chiến lược triển khai dần (canary deployment: cho mô hình mới phục vụ một phần nhỏ traffic trước, so sánh hiệu năng, rồi mới chuyển toàn bộ nếu ổn).
❌ Lỗi thường gặp: Chỉ lưu mô hình mà quên lưu scaler/encoder đi kèm, khiến dữ liệu mới trong production bị xử lý sai cách so với lúc huấn luyện.
✅ Best Practice: Luôn viết endpoint kiểm tra sức khỏe (health check, ví dụ GET /health) để hệ thống giám sát biết API còn hoạt động hay không.

🎯 Tổng kết Chương 36

  • Quy trình deploy cơ bản: lưu mô hình → viết API → đóng gói → triển khai.
  • Flask đơn giản, lâu đời; FastAPI nhanh hơn, tự động validate và sinh tài liệu.
  • Luôn lưu toàn bộ Pipeline, không chỉ riêng mô hình, để đảm bảo tính nhất quán khi xử lý dữ liệu mới.
  • Model Drift (Data Drift/Concept Drift) khiến mô hình tệ dần theo thời gian mà không báo lỗi kỹ thuật — cần theo dõi metric trên dữ liệu mới và retraining định kỳ.

37.1. Docker — "Nó chạy trên máy tôi mà!"

Câu than phiền kinh điển trong lập trình: code chạy tốt trên máy người viết nhưng lỗi trên máy khác, do khác phiên bản Python/thư viện/hệ điều hành. Docker giải quyết triệt để vấn đề này bằng cách đóng gói toàn bộ ứng dụng + môi trường (Python, thư viện, cấu hình hệ thống) vào một container — chạy giống hệt nhau ở bất kỳ đâu.

Dockerfile (công thức) → build thành Image (bản đóng gói tĩnh) → chạy thành Container (instance sống).
dockerfile 
# Dockerfile
FROM python:3.11-slim

WORKDIR /app

# Copy file requirements trước để tận dụng cache của Docker khi build lại
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy toàn bộ code ứng dụng, bao gồm model.pkl và app_fastapi.py
COPY . .

EXPOSE 8000
CMD ["uvicorn", "app_fastapi:app", "--host", "0.0.0.0", "--port", "8000"]
bash 
# Build image từ Dockerfile
docker build -t my-ml-api .

# Chạy container từ image vừa build, map cổng 8000 của container ra cổng 8000 máy host
docker run -p 8000:8000 my-ml-api
  1. FROM python:3.11-slim — chọn "base image" có sẵn Python 3.11 phiên bản gọn nhẹ, làm nền cho image của mình.
  2. COPY requirements.txt . rồi RUN pip install ... trước khi copy toàn bộ code — thứ tự này giúp Docker tận dụng cache: nếu chỉ sửa code mà không đổi thư viện, bước cài đặt thư viện (thường lâu nhất) không cần chạy lại.
  3. EXPOSE 8000 — khai báo container sẽ lắng nghe ở cổng 8000 bên trong.
  4. docker run -p 8000:8000 — "map" cổng 8000 của container ra cổng 8000 của máy thật, cho phép truy cập API từ bên ngoài container.

37.2. Git & GitHub — quản lý phiên bản mã nguồn

Git là công cụ theo dõi lịch sử thay đổi của code theo thời gian, cho phép nhiều người cùng làm việc mà không ghi đè lên nhau. GitHub là nền tảng lưu trữ trực tuyến cho các "kho" (repository) Git, hỗ trợ cộng tác nhóm.

bash 
# Khởi tạo Git cho một dự án ML mới
git init
git add .
git commit -m "Khởi tạo dự án: pipeline tiền xử lý + Random Forest baseline"

# Kết nối với kho GitHub từ xa và đẩy code lên
git remote add origin https://github.com/ten-ban/du-an-ml.git
git push -u origin main

# Tạo nhánh riêng để thử nghiệm ý tưởng mới, không ảnh hưởng code chính
git checkout -b thu-nghiem-xgboost
# ... chỉnh sửa code, thử XGBoost thay Random Forest ...
git add .
git commit -m "Thử nghiệm XGBoost, so sánh F1-score với Random Forest"
git push origin thu-nghiem-xgboost
LệnhÝ nghĩa
git add .Đánh dấu các thay đổi sẽ được lưu vào commit tiếp theo
git commit -m "..."Lưu một "điểm mốc" trong lịch sử, kèm mô tả rõ ràng đã thay đổi gì
git checkout -b ten-nhanhTạo và chuyển sang nhánh (branch) mới, tách biệt khỏi code chính
git pushĐẩy các commit từ máy local lên kho lưu trữ từ xa (như GitHub)
💡 File .gitignore cho dự án ML
Luôn tạo file .gitignore để loại trừ những thứ không nên đưa lên Git: file dữ liệu lớn (*.csv, *.parquet), model đã huấn luyện nặng (*.pkl, *.h5), môi trường ảo (venv/), và file cache của Jupyter (.ipynb_checkpoints/) — giữ kho Git gọn nhẹ, chỉ chứa code và cấu hình.
🔴 Vì sao không nên commit trực tiếp file dữ liệu/model lớn?
Git được thiết kế để theo dõi thay đổi văn bản hiệu quả (code), không phù hợp với file nhị phân lớn — mỗi lần thay đổi nhỏ vẫn lưu lại toàn bộ file, khiến kho phình to rất nhanh. Với dữ liệu/model, nên dùng công cụ chuyên biệt như DVC (Data Version Control) — sẽ học ở phần MLOps tiếp theo.

✅ Best Practice: Luôn viết .gitignore ngay từ đầu dự án, và dùng nhánh (branch) riêng khi thử nghiệm ý tưởng mới thay vì sửa trực tiếp trên nhánh chính.
